# Spydell Roadmap

Roadmap нужен только полному маршруту Spydell (несколько capabilities или волн). Протокол —
[sdd-coordination.md](../spydell/references/sdd-coordination.md), методы — [planning-methods.md](../spydell/references/planning-methods.md).

## Вход и границы

Вход: концепция, решения, требования, текущие возможности и ограничения; для пересмотра — проверенная реализация
предыдущей волны, её review и QA. Данных мало — предварительный roadmap с открытыми вопросами; заблокированный срез
готовым не помечай. Выход — `roadmap.md` по [artifacts.md](../spydell/references/artifacts.md). Код, changes, тикеты
и стенды из плана не создавай; сроки, доступность людей и оценки не выдумывай.

Во встроенном режиме ведущий владеет диалогом и `map.md`, ты меняешь roadmap и возвращаешь вопросы. Самостоятельно —
`spydell-grilling` только для существенных приоритетов, границ и компромиссов; начни с короткой карты: эпики, срезы,
зависимости, волны, открытые решения и что нужно от владельца.

Один план — три представления, можно разделами одного документа: продуктовое (польза и почему такой порядок), объём
поставки (эпики, срезы, обязательное, отложенное, исключённое, приёмка) и выполнение (зависимости, ресурсы, интеграция,
выпуск, свидетельства). Желаемый приоритет — не технический блокер, топологический слой — не календарное обещание.

## Построение

1. Свяжи требования с целями и решениями. Приоритет — по пользе, силе свидетельств, риску и срочности; effort —
   только с основанием. Опыт пользователя важнее удобства реализации: меньше срезов, но доведённых; основной сценарий
   первым; каждая опция обоснована; пользователь — это и потребитель API, и тот, кто сопровождает код. Эпик, который
   можно не делать или закрыть существующим, правилом или настройкой ([лестница](../spydell/references/method.md)),
   уходит в «Вне области» с причиной; решает владелец.
2. Эпики с самостоятельной пользой → узкие вертикальные срезы; срез — наименьший прирост, который даёт главное.
   Небольшой эпик — один change, большой делится. Мера среза — его change укладывается в одну сессию apply: ориентир —
   до 15 задач; больше — дели. Подготовительный рефакторинг, без которого новое поведение не встаёт чисто, — отдельным
   срезом или первой группой задач, не вперемешку с поведением. Дальним волнам детальные tasks не нужны; для ближайшей
   зависимой — предварительный change без tasks.
3. Гипотезу пользы («почему A помогает цели») отделяй от зависимости выполнения («какой результат A нужен B»);
   непроверенный эффект — гипотеза.
4. Блокирующая связь: требуемый результат, причина, тип (продуктовая, решение/знание, контрактная, интеграционная,
   ресурсная), критерий готовности, свидетельство; блокирует старт, интеграцию или выпуск. Предпочтение порядка —
   не блокировка. Дизайн уровня А — зависимость «решение» перед `ready-for-spec`; дизайн уровня В — отдельный срез
   с контрактной зависимостью, общий дизайн идёт на волну впереди ([ux-design.md](../spydell/references/ux-design.md)).
5. `python3 <spydell>/scripts/check.py roadmap roadmap.md` находит roadmap без срезов, отсутствующие ссылки, циклы и `ready-for-build`
   при открытых решениях. Цикл — пересмотри границу срезов, общую предпосылку или условие связи; волн неразрешённому
   циклу не назначай; продуктовый выбор — в spydell-grilling. Условный вариант разбиения — отдельно от действующего плана.
6. Волны — по доступным результатам и общей пользе. Wave 0 — только для конкретного блокера, не «вся инфраструктура
   сначала». Внутренний API без внешних потребителей переводи целиком, удаляя старый в той же волне; expand–contract —
   для внешних контрактов и данных. Развёртывание отделяй от включения: флаги и поэтапный выкат.
7. После каждой волны — состояние, критерии входа и выхода; для миграций после дизайна — обратимость, данные,
   совместимость, откат. Наступающие с волной условия пересмотра упрощений из карты отметь у неё.
8. До технического дизайна параллельность лишь логическая; после — проверь общие контракты, capabilities, файлы,
   миграции, окружения. Отдельные ветки не доказывают независимость. Общие контракты (схема данных, формат сообщений,
   интерфейсы) — одной очередью с одним владельцем, срезы поведения поверх — параллельно, интеграция — у координатора.
   Срез по нескольким репозиториям — по [multi-repo.md](../spydell/references/multi-repo.md); раздача работы агентам
   и сессиям — по [orchestration.md](../spydell/references/orchestration.md).
9. Срез не ждёт действия, которое владелец отложил или запретил (публикация, выпуск, внешнее согласование).
10. Перед передачей первой волны в OpenSpec покажи владельцу нарезку: срезы, их крупность, блокирующие связи, что
    слить или разбить. Его ответ — решение с кодом в карте; без него roadmap предварителен.
11. Каждое требование покрыто, каждый срез обоснован; все дальние работы `ready-for-build` не помечай.

## Карточка среза

```text
Стабильный ID / название / цель и ссылки на требования
Результат и приёмка / входит / исключено или отложено
Решения и неизвестные / уровень определённости
Предшественник -> требуемый результат -> почему нужен -> критерий готовности
Тип зависимости / старт, интеграция или выпуск / свидетельство и владелец подтверждения
Волна / состояние после неё / условия параллельности
Исполнение: <класс>/<effort> / Параллельно с: <ID срезов>
OpenSpec change / capabilities (ADDED или MODIFIED) / актуальная ревизия источников / проверки после реализации
```

Состояния `candidate`, `needs-decision`, `ready-for-spec`, `ready-for-build` — обозначения плана, не статусы OpenSpec;
ID не меняется при перестановке. Для программы — таблица раздела `## Срезы`:
`ID | Срез | Волна | Состояние | Предшественники | Change | Репозиторий`, по желанию ещё `Исполнение | Параллельно с`;
карточка `### <ID> — название` под ней — описание среза, открытые решения в ней — коды `R<n>_Q<n>`. Без таблицы
программа читает карточки: строки `Предшественник:`, `Состояние:`, `Волна:`, `Change:`, `Исполнение:`,
`Параллельно с:`. По этим данным работают `check.py` и дашборд
([artifacts.md](../spydell/references/artifacts.md)).

## План исполнения волны

Для волны, которая идёт в реализацию, — раздел roadmap: какие срезы идут параллельно и почему они независимы
(пути, контракты, миграции, окружение — по [orchestration.md](../spydell/references/orchestration.md)), сколько
исполнителей одновременно, класс и effort ведущего волны, ступень доверия автономного прогона, если он есть. В карточке
среза — `Исполнение: <класс>/<effort>` (сильная, средняя или лёгкая / низкий, средний, высокий или максимальный)
и `Параллельно с: <ID>` — срезы той же волны без связи «предшественник». Пиши классом и effort, а не названием
модели: модель выбирает `models.md` среды исполнения. До технического дизайна параллельность логическая, после —
подтверждённая.

## Карта capabilities

Перед передачей в OpenSpec: срез → capability (существующий путь из `openspec list --specs` или новое имя) →
ADDED или MODIFIED → change → волна. Два change одной волны с MODIFIED одной capability — упорядочи, объедини
или выдели общую предпосылку. Имя capability — устойчивое поведение системы, а не работа в срезе. Граф зависимостей
и карта capabilities — диаграммой по [planning-methods.md](../spydell/references/planning-methods.md); без Gantt с датами.

## Стратегия тестирования

На полном пути — раздел roadmap на 10–15 строк: кто выполняет ручное QA, стенды, допустимый риск, нефункциональные
проверки, браузеры и устройства, данные, что автоматизировать. Развилки — через spydell-grilling, факты (фреймворки, CI,
стенды, сиды) агент выясняет сам. Стратегия влияет на нарезку, зависимости (стенды и данные — ресурсные, ручные
ворота — выпуска) и приёмку срезов. Отдельных волн тестирования нет, кроме блокирующего среза инфраструктуры тестов
и регрессии перед выпуском по желанию владельца. Пороги качества кода — в `CONSTRAINTS.md`, здесь не повторяются.

## Пересмотр после реализации

По [wave-review.md](../spydell/references/wave-review.md). Предыдущие specs не доказывают готовность: проверь код,
сборку, свидетельства, изменения контрактов, UI и решений; обнови зависимости и последующие срезы. Independent
`spydell-spec-review` запрашивает ведущий; автор roadmap свой план прошедшим ревью не объявляет. Зависимые specs
предварительны до сверки с предшественником.

Накопившиеся правки уже реализованных контрактов собирай в один change, пока владелец не закроет список, и планируй
вставной волной со своим ID без перенумерации; отметь, какие specs следующих волн она меняет. В OpenSpec это MODIFIED
против заархивированных specs; несколько changes — один координатор и общий отчёт приёмки. В начале roadmap — текущее
состояние и ближайшие ворота, история волн — ниже.

В чате — ссылки и главные решения, без всего backlog. Заканчивай строкой «Не проверено: …».
