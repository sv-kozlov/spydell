# Передача дерева фронтенду

Размести дерево в UI-спецификации экрана или описании среза. Укажи сценарий, ссылку на исходный вид
и версию, если она известна. Индекс хранит возможности библиотеки. Здесь опиши, какие из них использует экран.

## Дерево и записи узлов

1. Дай каждому значимому узлу имя в пределах экрана. Отступ обозначает визуального родителя.
   В строке укажи роль или библиотечный компонент, при повторении — источник элементов, при условном показе —
   условие. Обозначь владельца общей панели, прокрутки и переключаемого содержимого.
2. Для экземпляра дай ссылку на оригинал через индекс, фактические значения свойств и заполнение слотов.
   Для обычного контейнера достаточно имени и правила компоновки. Заявленное соответствие компоненту
   фронтенда подкрепи ссылкой на символ. Предлагаемый компонент явно пометь.
3. Для узла с несколькими конфигурациями перечисли **допустимые на этом экране** значения по осям ниже.
   Назови начальное значение или правило выбора. Отметь ограничения сочетаний. Общий набор вариантов
   исходного компонента можно дать ссылкой, когда экран использует его целиком.

| Ось | Что передать |
| --- | --- |
| Вариант компонента | Настройка (например, размер), выбранное значение и кто его задаёт. |
| Состояние | Условия входа и выхода, видимое содержимое и доступные действия. |
| Вид представления | Поддержанные виды (список, сетка), способ переключения и сохраняемые данные. |
| Тема | Поддержанные темы, откуда наследуются, семантические токены и локальные исключения. |
| Адаптивность | Условие изменения дерева, порядка или вида. Порог возьми из требований или токена. |

Опиши общую тему и виды один раз на узле-владельце. В потомках указывай отличия. Перечисляй только применимые
оси. Если показан один вид, остальные пометь как неподтверждённые лишь тогда, когда от них зависит реализация.
Значения по умолчанию, автопереключение вида и поддержка тёмной темы требуют собственного основания.

## Пример фрагмента передачи

Условный экран результатов поиска. Имена компонентов и токенов ниже иллюстрируют формат.

```text
SearchResults
├─ Toolbar
│  └─ ViewSwitch → Controls/SegmentedControl [если доступны оба вида]
└─ ResultsBody [владеет состоянием данных и прокруткой результатов]
   ├─ LoadingIndicator [initialLoading]
   ├─ ResultsCollection [ready] → ResultItem × число результатов
   ├─ EmptyMessage [empty]
   └─ ErrorNotice [error] → RetryButton
```

- **SearchResults.** Темы light и dark наследуются от приложения. Фон и текст используют роли
  surface и text.primary из дизайн-системы. Дерево и действия одинаковы в обеих темах.
- **Toolbar / ViewSwitch.** В широком окне доступны list и grid, начальный вид — list.
  Ниже проектного порога compact доступен только list, переключатель скрыт. При смене вида запрос сохраняется.
- **ResultsBody.** При открытии начинается первый запрос. До ответа виден initialLoading. Непустой ответ даёт
  ready, пустой — empty, сбой — error. При повторе из error сообщение остаётся видимым, RetryButton недоступна
  до завершения запроса. Результат определяет следующее состояние по тем же правилам. Для list и grid они одинаковы.
- **ResultsCollection / ResultItem.** В list используется вариант row, в grid — tile.
  Слот title получает название результата. Сочетания list + tile и compact + grid исключены.

Разработчик получает границы компонентов, допустимые свойства и переходы. Для приёмки выбери случаи,
которые различают правила: переключение вида с сохранением запроса, сужение окна при активной сетке,
первое открытие, ошибка с повтором и читаемость сообщения в обеих темах. Привяжи их к соответствующим узлам.
