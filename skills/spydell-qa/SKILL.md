# Spydell QA

Проверяй поведение так, как его увидит пользователь. Ожидаемый результат берётся из согласованных источников,
а не из кода. Работай внутри семейства Spydell: [маршруты](../spydell/SKILL.md) задают масштаб,
[wave-review.md](../spydell/references/wave-review.md) — место QA в приёмке волны.

## Входы

Прочитай правила AGENTS.md и навыки проекта для тестирования, а также раздел карты «Требования к ревью»:
прошлые классы дефектов проверь, опровергнутое повторно не поднимай.

- **Ранний** — после specs. На полном пути подготовь раздел стратегии тестирования roadmap
  ([spydell-roadmap](../spydell-roadmap/SKILL.md)): развилки владельца — через `grilling`, факты выясняй сам.
  Затем черновик `acceptance/qa-plan.md` по инструкции схемы: `openspec instructions qa-plan --change <имя>`.
- **Поздний** — по сборке: дополни план регрессией по фактическому diff, проведи прогон и отчёт.
  Перепроверка после исправлений — проваленные кейсы и обоснованная регрессия.
- **Без specs** (legacy, срочная ветка) — ожидаемое поведение из тикета, PR или ответа человека.
  При неясности задай вопрос; из кода ожидаемое поведение не выводи.

Масштаб — по таблице маршрутов: «код» — 1–3 smoke-кейса строкой в итоге, если изменение видно пользователю;
«спека» — короткий план при UI; полный путь — полный план. Без пользовательского взаимодействия план — одна строка
о том, почему QA неприменимо. Что можно проверить тестом, оформляется тестом в реализации
([сначала скрипт](../spydell/references/method.md)); в план идёт только то, что скриптом не проверить.

## План

Кейс: ID, роль, предусловия, точные действия, ожидаемый результат, способ наблюдения, сценарий, исполнитель.
Ожидаемый результат — из сценариев specs. Включи сквозные пути между changes волны.
Кейсы с необратимыми действиями и оценкой на глаз выполняет человек.
Для рискованного интерфейса добавь одну исследовательскую сессию: что ищем и таймбокс.
Если есть согласованные макеты, сверь с ними реализацию. Проверь доступность: клавиатурный путь, фокус,
подписи, сообщения о состоянии; контраст — `npx @google/design.md lint`, если есть `DESIGN.md` и CLI доступен.
Визуальная регрессия — только при уже существующей инфраструктуре.

## Прогон

- Исполнитель — отдельный агент или сессия: получает план и сборку, но не контекст реализации.
  Если ты и есть исполнитель, прогоняй сам и не запускай ещё одного.
- Действуй через реальный интерфейс любым доступным браузерным или computer-use инструментом.
  Нет инструмента — кейс «заблокирован», план уходит человеку чек-листом.
  API и CLI годятся для подготовки и диагностики, но не заменяют проверяемый интерфейс; автоматический прогон
  операционного пути не заменяет визуальные и интерактивные кейсы.
- Тестовые данные и доступы — ссылками на тестовые аккаунты, сиды и env-файл. Можно попросить человека
  подготовить окружение (например, `.env.test`: URL стендов, тестовые аккаунты, ключи тестовой среды).
  Секреты не попадают в план, отчёт и вывод.
- Стенды и данные — по правилам проекта. Рабочие службы и реальные приборы — только человек,
  с его разрешения в исполняющей сессии.

## Отчёт и дефекты

Отчёт — `acceptance/qa-report.md` в OpenSpec change, иначе по [artifacts.md](../spydell/references/artifacts.md):
версии плана и сборки, результат каждого кейса, доказательства, дефекты. Статусы: пройден, не пройден, заблокирован;
невыполненный кейс не считается пройденным. Дефект: ID, важность (blocker, major, minor, cosmetic), шаги,
ожидаемое и фактическое, доказательство, кейс. В трекер дефекты идут только по просьбе или если трекер настроен.
Отчёт передаётся code reviewer вместе с diff, даже если все кейсы прошли.

При перепроверке сохраняй прежние неуспешные результаты, отмечай ревизии повторов и применимость
неповторённых кейсов. Расхождение с согласованным ожиданием — дефект; если ожидание не согласовано,
это вопрос ведущему, а не дефект.

## После прогона

- Стабильно проходящие кейсы перенеси в e2e проекта, если фреймворк уже есть; новый ради этого не заводи.
- Расхождения с макетами и новые паттерны интерфейса передай ведущему для каркаса UX и Do's and Don'ts в `DESIGN.md`.
- API проверяй автотестами в проекте. Один раз спроси, нужен ли пакет для QA-инженера —
  коллекция Postman или Insomnia и шаблон окружения без секретов; делай его только по ответу «да».

## Границы

Не исправляй код и specs, не принимай продуктовых решений. Во встроенном режиме верни ведущему вердикт,
дефекты по одной строке (важность, место, суть) и ссылки; `map.md` не меняй.
Заканчивай ответ строкой «Не проверено: …».
