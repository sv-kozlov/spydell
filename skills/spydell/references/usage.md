# Как использовать Spydell в совместном SDD-процессе

Эту справку выдавай только когда пользователь просит объяснить использование, установку, настройку или совместную работу Spydell. Не добавляй её автоматически в анализ, карту, требования, RFC или итоговое сообщение обычной задачи.

## Что установить

Сам Spydell создаёт аналитические документы, но для полного совместного процесса нужны дополнительные capabilities. Перед началом соответствующего этапа проверь их наличие в списке доступных skills.

Семейство Spydell:

- `spydell` — единый вход от концепции к требованиям и координации порученного процесса;
- `spydell-roadmap` — эпики, срезы, зависимости, волны и пересмотр по результатам реализации;
- `spydell-spec-review` — независимое ревью документов и готовности следующих specs.

Минимальный набор для анализа и принятия решений:

- `grilling` — структурированный HITL-опрос материальных решений;
- `research` — проверка фактов по первичным и применимым источникам;
- `wayfinder` — карта и журнал решений для работы длиннее одной сессии;
- `domain-modeling` — уточнение терминов и границ модели, используемое Wayfinder для grilling-tickets.

`grill-me` — совместимый короткий вход, который вызывает `grilling`. Достаточно рабочего `grilling`; не нужно проводить оба опроса.

Для разработки по SDD дополнительно нужны:

- OpenSpec CLI;
- локально сгенерированный набор `openspec-*` skills для создания, продолжения, изменения, применения, проверки, синхронизации и архивирования change artifacts;
- профильный skill целевого репозитория или технологии для реализации;
- `code-review` для проверки качества кода отдельно от OpenSpec compliance verification.

По ситуации полезны `prototype`, `spydell-critic`, `spydell-evaluator`, `spydell-systems`, `spydell-ai-agents` и `spydell-triz`. Не устанавливай и не запускай их как обязательный ритуал, если их предмет не влияет на решение.

Если capability отсутствует, используй доступный `skill-installer`, plugin manager или официальный способ установки этой среды. Не копируй поведение отсутствующего skill в Spydell. Перед фазой, которая от него зависит, сообщи пользователю, чего не хватает и зачем; продолжай только те части работы, которым эта зависимость не нужна.

Для OpenSpec используй официальную инициализацию в целевом репозитории, чтобы skills соответствовали установленной версии CLI. После инициализации проверь, что CLI видит planning root и доступные change schemas. Не подменяй локальные инструкции OpenSpec запомненной процедурой из другой версии.

Выбирай OpenSpec skill по намерению, не смешивая их роли:

- `openspec-new-change` — создать change и остановиться перед наполнением;
- `openspec-propose` или `openspec-ff-change` — сформировать весь apply-ready комплект после прохождения ворот решений;
- `openspec-continue-change` — создать следующий разрешённый schema artifact;
- `openspec-update-change` — согласованно изменить уже существующие planning artifacts без правки кода;
- `openspec-apply-change` — реализовать tasks с профильным implementation skill;
- `openspec-verify-change` — проверить соответствие реализации change artifacts;
- `openspec-sync-specs` и `openspec-archive-change` — синхронизировать нормативные specs и завершить lifecycle после проверки.

`openspec-explore` можно использовать для лёгкого исследования внутри уже выбранного OpenSpec-контекста. Не веди параллельно одинаковое discovery в нём и Spydell: выбери одно каноническое место, а второму передай только итог и ссылки.

## Краткий процесс

1. Создать концепцию: проблема, люди, картина будущего, сквозные истории и открытые аспекты без архитектуры.
2. Прояснить существенные аспекты через grilling; для многосессионного фронтира использовать Wayfinder.
3. Сформировать наблюдаемые требования и приёмку; затем вызвать `spydell-roadmap` для срезов и волн.
4. Передать готовый срез в OpenSpec: proposal со ссылками и ревизиями, specs, затем design и tasks.
5. Выполнить независимый `spydell-spec-review` перед реализацией; устранить и перепроверить замечания.
6. При порученной реализации выполнить волновой цикл из [wave-review.md](wave-review.md):
   обычные тесты, code review до закрытия замечаний, UI QA с планом/отчётом, повторное code review.
7. Через `spydell-spec-review` сверить документы и решения с фактическим результатом,
   затем пересмотреть зависимые specs следующей волны и её готовность.
8. Применить соответствующие OpenSpec verify/sync/archive в пределах поручения и правил проекта.

Grilling уместен на любом уровне при существенном выборе. Не запускай повторный опрос без новых оснований.
При новом продуктовом выборе вернись к решению, а не переписывай требования под случайно получившийся код.

## Примеры обращений

- «Spydell, разверни идею в концепцию без технического дизайна, затем обсудим открытые аспекты».
- «Spydell roadmap, разложи согласованные требования на эпики, волны и зависимости».
- «Spydell spec review, проверь готовность следующей волны по реализации, review и QA предыдущей».

## Где создаются артефакты

Корень комплекта всегда называется `.spydell` и остаётся видимым для Git, если проект отдельно не исключает его:

- `<project-root>/docs/.spydell/<project-slug>/`, если в корне есть `docs/`;
- иначе `<project-root>/doc/.spydell/<project-slug>/`, если в корне есть `doc/`;
- иначе `<project-root>/.spydell/<project-slug>/`.

Старый каталог `spydell/` без точки требует согласованной миграции; новый параллельный комплект рядом с ним не создаётся.

## Как выбрать короткий маршрут

- Ясное небольшое изменение: Spydell → OpenSpec → implementation/verify.
- Большой проект: concept → аспекты/Wayfinder → requirements → spydell-roadmap → OpenSpec → wave review.
- Уже есть согласованный change contract: не повторять discovery; сразу проверить readiness и перейти в OpenSpec.
- Реализация выявила новый выбор: приостановить apply → Wayfinder/HITL → Spydell/OpenSpec update → продолжить apply.

## Что не дублировать

- Не вести в Spydell параллельные decision-файлы для решений, уже живущих в Wayfinder.
- Не копировать исследования и полное rationale в OpenSpec scenarios.
- Не превращать OpenSpec tasks в Wayfinder decision tickets.
- Не считать OpenSpec validate заменой критики, code review, тестов или оценки реальной полезности.
- Не подменять профильные implementation/QA skills ведущим Spydell: он координирует их в порученной области.
