# Совместная работа Spydell, Wayfinder и OpenSpec

Используй этот протокол, когда анализ должен перейти в разработку по SDD. Он определяет границы и передачу результата, но не повторяет процедуры других скиллов. При подключении другого скилла прочитай его актуальный `SKILL.md` и следуй ему.

## Последовательность и область

Для сырой идеи: concept → прояснение аспектов → продуктовые требования → roadmap → OpenSpec specs → design → tasks.
Первый документ допускает неизвестные; не запускай полный технический опрос до общей картины.
Готовые решения повторно не обсуждаются. Grilling применяется на любом уровне только к существенному выбору.
При вызове grilling передай границы уровня явно: concept/clarify допускают документ с открытым фронтиром;
его общий запрет planning/acting до action contract не блокирует этот черновик.
Контракт и завершённый фронтир требуются для зависимого дизайна/реализации соответствующего среза,
а не для всех дальних волн сразу. Это адаптация grilling к выбранному пользователем процессу Spydell.
Новые навыки процесса входят в `spydell-*`; существующие Matt/OpenSpec/QA-навыки остаются зависимостями.
Spydell координирует порученный процесс, но не подменяет implementation skills.

Для большой инициативы `spydell-roadmap` выделяет эпики и срезы с требованиями, зависимостями и волнами.
Продуктовый порядок, границы backlog и фактический план выполнения различаются даже внутри одного документа.
`spydell-spec-review` проверяет срез перед реализацией и после каждой волны.
Для маленького ясного изменения не создавай полный комплект и карту Wayfinder ради процедуры.

## Разделение ответственности

| Слой | За что отвечает | Чем не является |
|---|---|---|
| Spydell | постановка проблемы, исследование, критика, варианты, итоговая связная формулировка требований/RFC | трекер решений, OpenSpec workflow или реализация |
| Wayfinder | канонический журнал ещё не принятых и принятых решений, их зависимостей и границы destination | хранилище исследований, готовая спецификация или backlog реализации |
| OpenSpec | нормативный change contract для реализации: capabilities, requirements/scenarios, design и tasks согласно активной schema | место для исследования проблемы или неявного принятия продуктовых решений |
| Реализация и проверка | код, тесты, эксплуатационные доказательства и проверка соответствия change artifacts | повод молча изменить ранее утверждённый замысел |

Один факт, решение или требование должно иметь одно каноническое место. Остальные документы дают краткое следствие и ссылку, а не копируют обоснование целиком.

## Когда подключать соседние скиллы

- `grilling` — когда остаётся материальный выбор пользователя. `grill-me` является совместимым входом в тот же `grilling`; не запускай два отдельных опроса.
- `domain-modeling` — когда спор о терминах, границах сущностей или долгоживущем архитектурном решении влияет на контракт. `CONTEXT.md` остаётся словарём, ADR — редким обоснованием; ни один из них не заменяет требования.
- `research` — для устанавливаемых фактов. Не превращай исследовательский вывод в решение пользователя.
- `prototype` — когда решение нельзя надёжно принять без дешёвого конкретного объекта для реакции. Прототип не считается реализацией destination.
- `wayfinder` — когда фронтир решений и зависимостей не помещается в одну рабочую сессию, решения должны приниматься несколькими сессиями/участниками или нужен устойчивый журнал HITL-выборов. Для небольшого уже ясного изменения не создавай карту ради процесса.
- `spydell-critic` — по явному запросу на стресс-тест. Finding не становится новым требованием до решения пользователя.
- `spydell-evaluator`, `spydell-systems`, `spydell-ai-agents` — только когда их предмет способен изменить решение; встроенный специалист не запускает следующий оркестратор.
- `spydell-triz` — когда выбор свёлся к компромиссу между двумя свойствами и стоит попытаться снять противоречие. Концепции из `triz.md` становятся требованиями только после решения пользователя.
- OpenSpec skills — после готовности решений либо для изменения уже существующего change. Выбирай актуальный локальный OpenSpec skill по намерению пользователя; не воспроизводи его CLI-процедуру внутри Spydell.
- Проектный implementation skill — во время применения OpenSpec; `code-review` проверяет качество кода, а OpenSpec verify отдельно проверяет соответствие артефактам. Эти проверки дополняют, а не заменяют друг друга.

## Переход Spydell → Wayfinder

Передавай в Wayfinder не копию всех документов, а:

1. destination и границы;
2. подтверждённые факты со ссылками;
3. уже принятые решения;
4. материальный открытый фронтир и зависимости вопросов;
5. явно исключённое.

Если Wayfinder активен, закрытая карточка является каноническим местом соответствующего выбора. Spydell `map.md` только ссылается на карту/карточки. После закрытия существенного фронтира пересобери целевые Spydell-документы в связный контракт и пометь ранние конфликтующие рекомендации историческими или заменёнными.

Не создавай одновременно `decisions/*.md` Spydell и Wayfinder tickets для одного решения. Локальные Spydell decisions нужны только когда Wayfinder не используется.

## Roadmap и handoff среза

В OpenSpec передавай согласованный срез ближайшей волны, а не всю неопределённую инициативу.
В proposal фиксируй источник и ревизию, epic/slice ID, требования, решения, предшественники,
условия готовности, общие capabilities и отложенный scope. Это поля документа, не выдуманные metadata CLI.
Различай текущую базу specs и ожидаемые результаты активных changes.
Созданный файл предшественника не означает, что требуемое поведение уже реализовано и проверено.

До OpenSpec не должно быть блокирующего продуктового выбора выбранного среза.
Технические trade-offs можно уточнять после specs; при изменении поведения возвращайся в продуктовый диалог.
Для зависимой следующей волны допустим предварительный change: proposal и черновые specs с явной пометкой
«предварительный», без tasks. Apply не начинается до приёмки предшественника и пересмотра этих specs.
Для постепенного режима используй new/continue, для уже готового среза допустим propose/ff.
Выбирай доступную schema с порядком specs → design; default spec-driven может разрешать их независимо.
Если менять schema не поручено, соблюдай порядок при генерации и явно не обещай машинного контроля.
Не редактируй сгенерированные skills или CLI ради дублирования протокола.

## Ворота передачи в OpenSpec

OpenSpec можно создавать, когда:

- назначение изменения и наблюдаемый успех определены;
- продуктовый контракт поведения выбранного среза подтверждён;
- блокирующие продуктовые решения среза закрыты либо остаточные допущения явно приняты;
- факты отделены от решений и условий эксплуатации;
- требования непротиворечивы, проверяемы и имеют критерии приёмки;
- известны non-goals, отказ, повтор, конкуренция, partial state и rollout в применимом объёме.

Если эти условия не выполнены, продолжай Spydell или Wayfinder. Не используй генерацию всех OpenSpec artifacts как способ скрыть неразрешённый выбор правдоподобным текстом.

Продуктовый выбор, обнаруженный при написании specs, сразу задай пользователю, до независимой проверки пакета;
не заменяй его допущением в спецификации. Это штатная часть handoff, а не исключение.

## Проверка пакета до реализации

Перед apply независимый `spydell-spec-review` проверяет пакет. После правки подтверждённых замечаний до apply
проверку повторяет новый reviewer: сначала самостоятельно, затем сверяет закрытие прежних findings.
Каждый раунд добавляет источники, ещё не сверенные
с пакетом: код интегрируемой службы, SDK, legacy-реализацию, реальные данные. Технические расхождения
исправляются по источникам, новый продуктовый выбор возвращается пользователю.
Пакет готов, когда очередной раунд не находит подтверждённых замечаний.
Проверка после волны идёт по [wave-review.md](wave-review.md).

## Перенос в OpenSpec без дублирования

Используй финальный Spydell requirements/RFC как компактный основной вход, а Wayfinder — как арбитр спорных решений и источник rationale.

Переноси смысл по слоям:

`потребность → capability → normative requirement → scenario → design decision → implementation task → test/evidence`

- Proposal кратко фиксирует зачем и что меняется; не копирует исследование.
- Specs описывают наблюдаемое обязательное поведение и граничные сценарии; rationale остаётся в Spydell/Wayfinder.
- Design фиксирует выбранный технический механизм, ограничения и ссылки на решающие основания; не повторяет все scenarios.
- Tasks описывают проверяемые шаги реализации и доказательства; это не новый decision backlog.

Сохраняй стабильные идентификаторы требований или ссылки, если они уже есть. После создания проверь полноту трассировки, согласованность всех artifacts и выполни строгую валидацию средствами установленной версии OpenSpec.

## Источники истины по фазам

До создания OpenSpec приоритет имеют: последнее явное решение пользователя, затем закрытое каноническое решение Wayfinder, затем актуальный итоговый Spydell-документ. Research и critique остаются доказательствами и историей, но не отменяют более позднее решение.

После готовности OpenSpec именно активные change artifacts задают контракт реализации. Если обнаружено расхождение:

- уточнение формулировки без изменения замысла — согласованно обнови существующие OpenSpec artifacts;
- новый материальный выбор или изменение scope — останови реализацию, верни вопрос пользователю или в Wayfinder, затем синхронизируй итоговый Spydell и OpenSpec;
- новый технический факт без изменения поведения — обнови evidence/design в минимально нужных местах;
- дефект реализации — исправь код и тесты, не переписывая спецификацию под ошибку.

Не оставляй два противоречащих канонических документа. Старую рекомендацию явно пометь заменённой, если её сохранение полезно для истории.

## После каждой волны

Обязателен [wave-review.md](wave-review.md): code review до исчерпания замечаний, обычные тесты,
пользовательский QA по фактическому diff с планом и отчётом, повторное code review по этим артефактам,
затем цикл ревью/исправления specs, решений, документов и предпосылок следующей волны.
Пользовательский QA требуется для функций с участием пользователя; при отсутствии UI это обосновывается.
Следующие specs до сверки с проверенной реализацией предшественника предварительны.
Новые факты могут изменить roadmap; код не становится требованием автоматически.

## Цикл реализации

Для реализации используй актуальный `openspec-apply-change` и подходящий проектный skill. Отмечай task завершённым только вместе с требуемым свидетельством. Если код выявил проблему дизайна, не продолжай по инерции: используй процесс обновления OpenSpec, а при новом выборе — Wayfinder/HITL.

Перед архивированием разделяй проверки:

1. тесты и проектные quality gates;
2. code review для дефектов и сопровождаемости;
3. OpenSpec verify для полноты, корректности scenarios и соответствия design;
4. специализированную оценку реальной полезности, если она была частью критерия успеха.

OpenSpec archive/sync выполняй только соответствующим локальным skill после требуемых подтверждений; Spydell не перемещает и не синхронизирует change artifacts самостоятельно.

## Минимальная трассируемость handoff

Перед началом реализации должно быть возможно ответить ссылками:

- какая потребность оправдывает capability;
- где принято каждое нетривиальное решение;
- какой requirement и scenario выражают решение;
- какая task и проверка доказывают реализацию;
- какие риски приняты, кем и при каких условиях пересматриваются.

Трассировка должна помогать находить источник, а не создавать параллельную матрицу, которую невозможно поддерживать.
