# Обязательное завершение волны

Для порученной реализации волн полного маршрута или проверки их завершённости; «код» и «спека» проверяются по таблице
маршрутов в [SKILL.md](../SKILL.md). В задаче только на документацию опиши проверки, ничего не запускай. Ведущий
координирует профильные навыки реализации, ревью и QA, а не заменяет их. Компонент без своего OpenSpec change (SDK, CLI)
проходит тот же цикл: по завершении блока ведущий сам запускает независимое ревью. Сессии волны —
по [orchestration.md](orchestration.md).

## Проверяемая версия

Зафиксируй состав changes, базу и merge-base, проверяемые commit или сборку и ревизии документов; для незакоммиченного —
воспроизводимый снимок diff с базовым SHA. Проверяй и отдельные changes, и интегрированный результат.
Несколько репозиториев — по [multi-repo.md](multi-repo.md).

## Цикл

1. Обычные тесты и обязательные проверки проекта.
2. Точный diff — независимому code reviewer вместе с требованиями, контекстом, разделом карты «Требования к ревью»,
   правилами AGENTS.md и навыками проекта для ревью. Минимум две оси: качество кода (`ponytail-review`, иначе
   `code-review`; при нескольких стеках — reviewer на стек) и соответствие specs (`openspec-verify-change`, если включён,
   и матрица requirement → scenario → реализация → тест → статус). Есть `CONSTRAINTS.md` — проверь, что diff не понижает
   планку: пороги, подавления проверок, пропущенные или удалённые тесты, вырезанные assertions, заглушки.
   Reviewer читает через `git diff`/`git show`, в общей рабочей копии ничего не меняет (без checkout, reset, stash),
   тесты запускает в отдельном worktree. Широкую приёмку дели между reviewer по осям и файлам; прерванное ревью
   возобнови тем же reviewer. После существенной правки ревьюится весь актуальный diff.
3. Есть пользовательское взаимодействие — QA по [spydell-qa](../../spydell-qa/SKILL.md), поздний вход; нет —
   обоснуй неприменимость.
4. Повторное code review с планом и отчётом QA, даже если все кейсы прошли. Исправления возвращают в цикл тестов,
   ревью и перепроверки QA. Два исправления с общей предпосылкой провалили одну проверку — запиши предпосылку
   и проверь её наблюдением до следующего исправления.
5. Независимый `spydell-spec-review` документов текущей и следующей волны (отчёт оси соответствия из шага 2 можно
   использовать). Дефект — в коде; согласованное изменение — в источнике и зависимых документах; новый выбор —
   в spydell-grilling; устаревший текст — без изменения scope.
6. Замечания к документам устрани и перепроверь; ошибку переписыванием specs не согласовывай.
7. Сверь `shortcut:` в коде (`ponytail-debt`, если установлен) с реестром «Принятые упрощения»: пометка без условия
   пересмотра или без строки в реестре — замечание; наступившее условие — работа следующей волны.
8. Пересмотри specs следующей волны по проверенной реализации, QA и решениям; до этого они предварительны.
9. Уроки — по [spydell-retro](../../spydell-retro/SKILL.md).
10. Уборка git — по разделу ниже.

Нет следующей волны — финальное согласование документов инициативы.

## Уборка git

В каждом репозитории волны, после всех исправлений и до документа приёмки. Цель — история, которую человек
ревьюит по коммитам.

1. Резервная ветка до переписывания: `git branch backup/<волна> HEAD`.
2. Перекомпонуй коммиты ветки волны, которых ещё нет в общей ветке:
   - коммит — одно логическое изменение, которое проверяется само и могло бы стать отдельным PR;
   - порядок рассказывает историю: удаление перед перестройкой, падающий тест перед исправлением, контракт перед
     потребителями, каркас перед функцией;
   - размер: ориентир около 100 изменённых строк, до 300 — для одного логического изменения, больше 1000 — разбей;
     переименования, форматирование и сгенерированные файлы — отдельными коммитами, их объём не считается;
   - не слишком мелко: правки вида «исправил опечатку» и «по ревью» влей в коммит, к которому они относятся;
     тесты и документы — вместе с кодом, к которому относятся;
   - рефакторинг — отдельно от изменения поведения; сообщения — по соглашению проекта.
   Коммить чисто по ходу работы — шаг за шагом; уборка перегруппировывает, а не схлопывает волну в один коммит.
   Интерактивные режимы git агенту недоступны: используй fixup-коммиты с autosquash или пересборку от базы
   (`git reset --soft <база>` и коммиты по группам путей).
3. Итоговое дерево совпадает с резервным (`git diff backup/<волна> HEAD` пуст) — тогда вердикты ревью и QA остаются
   в силе; в документе приёмки укажи проверенную ревизию и ревизию после перекомпоновки. Дерево изменилось — затронутые
   проверки повторяются. По возможности каждый коммит проходит быстрые проверки, итог — обязательно.
4. Переписывай только неопубликованные коммиты или собственную ветку среза. Опубликованную собственную ветку —
   `git push --force-with-lease` с разрешения владельца или контракта прогона ([autonomy.md](autonomy.md)); общие ветки
   и ветки чужих срезов — никогда. Ветку среза переписывает только её владелец.
5. Убери: worktree слитых и завершённых задач (`git worktree remove`, затем `git worktree prune`); worktree
   с незакоммиченными правками — покажи владельцу и жди решения; слитые ветки задач — удали; резервную ветку — после
   слияния волны; временные файлы и артефакты сессий вне `.gitignore`.
6. В документ приёмки — список коммитов ветки волны: хеш, сообщение, размер.

## Политика ворот

Шкала: blocker, major, minor, cosmetic — общая для code review и `spydell-spec-review`. По умолчанию до ворот
закрываются все подтверждённые замечания. Владелец может задать другую политику решением с датой, на которое ссылается
roadmap: например, исправляются blocker, major и всё о корректности, безопасности, совместимости и данных, а minor
и cosmetic записываются с местом. Политика может разрешить начать зависимую реализацию следующей волны до ручных ворот
предыдущей — тогда эта работа предварительна и останавливается при неуспешном или заблокированном кейсе;
без такого решения зависимая реализация ждёт ворот.

## Закрытие

Раундов без лимита. Подтверждённое замечание устранено и перепроверено или записано, если политика позволяет;
опровергнутое закрыто с проверяемым основанием; спорное и непроверенное остаётся открытым. Перенос в backlog —
не исправление. Внешний блокер — сообщи и назови следующий шаг, успешные ворота не имитируй.

Итог волны — один документ приёмки: в OpenSpec change это `acceptance.md`, подробности — в `acceptance/`
([artifacts.md](artifacts.md)). Разделы: проверенные ревизии по репозиториям, тесты, ревью по осям, QA, повторившиеся
классы находок, «Не выполнено» (каждый пункт — «владелец: …; следующий шаг: …»; каждый не пройденный
или заблокированный кейс QA — отдельным пунктом с его ID), отметки задач. Перед закрытием —
[check.py](../scripts/check.py): `acceptance`, `qa`, `trace` по каталогам change (по одному на репозиторий) — и
`openspec validate <имя> --strict --json` в каждом корне OpenSpec (общий store — `--store <id>`). Найденное программой —
блокер, а не повод менять проверку. Ссылку на документ — в `roadmap.md`, состояние — в `map.md`.

Зависимая реализация следующей волны не начинается при блокирующих по политике замечаниях, неуспешных или
заблокированных обязательных кейсах или несогласованных предпосылках; независимые исследования и предварительные
документы могут идти. Закрытая волна не разрешает production rollout или публикацию.
