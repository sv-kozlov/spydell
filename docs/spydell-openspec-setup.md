# Spydell и OpenSpec: настройка проекта

Настроено 9 октября 2026 года на OpenSpec 1.14.1; 23 октября 2026 года проверено на 1.14.3.

## Применённые файлы

- [config.yaml](../openspec/config.example.yaml): контекст, правила артефактов, инструкции apply/archive.
- [schema.yaml](../openspec/schemas/spydell/schema.yaml): проектная схема `spydell`.
- [proposal](../openspec/schemas/spydell/templates/proposal.md): источники, срез и предпосылки.
- [spec](../openspec/schemas/spydell/templates/spec.md): проверяемое поведение и трассировка.
- [design](../openspec/schemas/spydell/templates/design.md): механизм после specs и условия интеграции.
- [tasks](../openspec/schemas/spydell/templates/tasks.md): реализация и свидетельства завершения волны.

Схема получена из `spec-driven` пакета `@fission-ai/openspec` 1.14.1 через `openspec schema fork`.
Основные изменения — зависимость design от specs, полный список apply.requires и дополнения шаблонов.
Сохранены upstream-правила delta-specs, включая полные MODIFIED-блоки и проверяемые задачи.
Для соблюдения лимита строк длинные инструкции перенесены без изменения смысла.

Стоимость сопровождения — сравнивать локальную схему с новым `spec-driven` после обновлений CLI.
`openspec update` обновляет сгенерированные навыки, но не заменяет эту проверку проектной схемы.
Простая альтернатива — одни инструкции config; она не задаёт зависимость design от specs в графе.

## Начало новой инициативы

1. Через Spydell сформировать концепцию, прояснить существенные аспекты в grilling и записать требования.
2. Через `spydell-roadmap` определить срез ближайшей волны, зависимости и критерии готовности.
3. Когда срез готов, создать change с явной схемой; затем пользоваться обычными OpenSpec skills.

```bash
openspec new change <change-name> --schema spydell
openspec instructions proposal --change <change-name> --json
openspec status --change <change-name> --json
```

`<change-name>` нужно заменить реальным именем. Продуктовый пилот этой настройкой не создан.
Для небольшой понятной задачи достаточно её согласованного запроса; искусственный комплект инициативы не нужен.
Схема выбирается для change и сохраняется в его `.openspec.yaml`.

## Завершение волны

В задачах фиксируются обычные тесты и независимое ревью точного diff, устранение замечаний,
пользовательский QA с планом по diff и ожидаемыми результатами по требованиям,
выполненный прогон и отчёт, повторное ревью кода по этим материалам.
После этого проверяются и согласуются specs, решения, design, документы и предпосылки следующей волны.
При правках повторяются затронутые проверки; существенные изменения кода требуют полного повторного review.

Используется один канонический отчёт волны, связанный со сборкой/diff и ревизиями документов.
Для волны из нескольких changes назначается координатор и проверяется интегрированный результат.
Без пользовательского взаимодействия записывается причина неприменимости соответствующего QA.
Отсутствие стенда, инструмента или обязательного свидетельства означает незавершённую проверку.

Подтверждённое замечание устраняется и перепроверяется по политике ворот; опровергнутое закрывается
с обоснованием reviewer. По умолчанию до ворот закрываются все подтверждённые замечания; решение владельца
с датой может оставить записанными minor и cosmetic, не отменяя саму проверку.
Спорные замечания остаются открытыми. Перенос дефекта в backlog не закрывает волну.
Следующие зависимые specs пересматриваются по фактической реализации и результатам предыдущей волны.
Независимое исследование может продолжаться. Последняя волна завершается сверкой итоговых документов.

## Что проверено

Использовался временный проект, отдельный от рабочей папки. Продуктовый код и UI не запускались.

| Проверка | Результат |
| --- | --- |
| `schema validate` и `schema which` | Валидная схема разрешается из проекта |
| Последовательное появление файлов | proposal → specs → design → tasks |
| Выдача instructions четырёх артефактов | Контекст, rules и шаблоны переданы |
| Выдача apply/archive | Собственные operationGuidance переданы |
| Полный тестовый change | `validate --strict` проходит |
| Удаление proposal/spec/design/tasks по одному | Apply каждый раз заблокирован |
| Change без metadata | Схема остаётся spec-driven |
| Явное skip_specs для отсутствующего behavior delta | Specs пропускаются штатным механизмом |

Для повторной проверки структуры:

```bash
openspec schema validate spydell --json
openspec schema which spydell --json
```

Для проверки конкретного настоящего change используйте
`openspec validate <change-name> --strict --no-interactive`.
Все существующие проектные changes в рамках этой настройки не перевалидировались.

## Границы автоматизации

`requires` управляет наличием артефактов одного change. CLI не проверяет готовность соседних волн.
Пустой файл считается существующим; один spec-файл удовлетворяет glob, даже если capability несколько.
`skip_specs: true` допустим только без изменения поведения, с явным основанием;
не используйте его для обхода требований.
Содержательную полноту и согласованность проверяет независимый reviewer.

Guidance передаёт требования агенту, но не является программной блокировкой archive или проверкой качества QA.
Готовность файлов и task counts не заменяют итоговый отчёт. Production rollout требует отдельного поручения.

Источники: [project config](https://openspec.dev/docs/project-config),
[schema contract](https://openspec.dev/docs/schemas/schema-yaml).
Возможности и ограничения проверены по пакету 1.14.1 и фактической выдаче CLI; на 1.14.3 повторены validate, new change и status.
